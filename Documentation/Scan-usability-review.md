# 扫描可用性复查

本次检查以 preview.12 对应主线源码为起点，重点区分“能读取并展示”与“能够安全修改”。验证使用唯一自有临时 fixture；不以真实用户缓存或废纸篓进行删除测试。

## 修复

1. **缓存被无关废纸篓权限连带阻塞**：原受保护路径检查会打开每个保护目录，包括个人废纸篓。即使缓存可读取，只要某个无关保护目录无法打开，所有候选都会在计算大小前失败。现改为锚定父目录并读取 no-follow 身份，保留重叠及身份保护，无需访问保护对象的内容。
2. **受保护或部分不可读的项目全部显示未知**：Caches / Trash 原来只从完整可删除清单取大小。现使用独立、预算受限的只读元数据统计，保留已知大小，并区分完整、部分与未知。清理仍要求原有完整清单。
3. **条目上限导致整份列表消失**：超出直属列表上限时保留已读取的行并提示覆盖不完整；Trash 不允许对不完整列表执行快照清空。大小统计有单项预算，避免一个庞大目录耗尽后续所有行。
4. **耗时检查缺少定位**：显示当前检查路径及大小统计／清理资格两个阶段；取消、Demo、目录上下文改变或旧请求结束后不会发布迟到进度。错误注明失败阶段与路径，部分读取原因可展开查看。

## 其他工作区的检查结论

- **Space**：Mole 的读取与原生清理授权分开。报告保留 complete / partial / unavailable / unknown，unavailable 不显示为 0；重叠概览不计算可相加比例。实际分析仍要求明确目录与临时写入确认，取消与资源限制由既有 supervisor 处理。外部分析器的安装兼容性由独立修复处理；本次没有扩展命令或权限。
- **Projects**：现有发现扫描已保留多根目录的可读结果、跳过原因及进度；限制以部分结果体现，不调用项目代码或 Git hooks。目录句柄、条目数和深度预算继续生效。未发现与本次缓存同源的“删除资格阻止只读发现”问题。
- **Docker**：库存读取与精确选择删除分开，镜像大小与共享／独占估计有区别，未知引用不会授权删除。API 超时、响应上限或身份变化保持失败／不确定，不能把不完整 daemon 库存伪装成完整引用证据。这个边界保留，不以放宽删除保护换取可用性。

## 自动化与验收边界

新增回归覆盖无关受保护目录不可读、目录重叠及链接、Home 中的 Git 元数据、ACL／祖先权限拒绝时保留大小、EACCES / EPERM 部分读取、未知与空目录、元数据统计不打开文件或跟随链接、预算公平、列表上限及迟到进度隔离。既有真实原生 Trash fixture 仍受 hosted-runner opt-in 和身份门槛约束。

源码静态检查不等于 Swift 编译。原生 Debug / Release / AddressSanitizer、既有中英文渲染和精确 SHA 的 CI 结果以 PR 记录为准。权限注入 fixture 不宣称复现所有 macOS TCC 策略；真实窗口、键盘和 VoiceOver 的人工验收仍需分别记录。
