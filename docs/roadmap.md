# 分阶段范围与验收

状态：历史专项规划，不是当前交付清单。当前 [preview.12](../website/content/changelog/0.1.0-preview.12.md) 已交付 Mole 新手准备、AI worktree 收尾、简化界面与菜单栏，以及此前的受限原生工作流。最新进度见 [统一 Roadmap #40](https://github.com/cosZone/MoeKit/issues/40)；真实生产安装更新及完整原生交互仍待验收。以下阶段保留早期规划语义，不能据此认定所有能力都已实现。

## MVP 范围

MVP 分阶段形成，但只有通过对应安全门槛的能力才会进入可执行版本。

| 能力 | MVP 计划 | 后续扩展 |
| --- | --- | --- |
| 发现 | 用户选定根目录、手动添加仓库、识别 `.git` 文件与目录、归组 linked worktree | 更多已验证工具目录适配、多个仓库组成的项目 |
| 工作区检查 | 本地改动、未跟踪/忽略内容、branch/HEAD、锁、操作中状态、离线/未知 | 更细的活动线索、稀疏/复杂布局支持 |
| 空间 | 按需计算 checkout 与候选产物大小；排除重叠与共享对象重复统计 | 更细的分配空间信息和扫描性能优化 |
| 产物清理 | 极少量、明确路径、经过验证的产物规则；人工选择和审核 | 更多语言生态、共享开发缓存、适配器目录 |
| worktree 退役 | 仅普通、已完整检查的 clean linked worktree；默认保留分支；不用 force | 经专门测试的复杂布局与有限归档恢复 |
| 分支 | 清晰库存、比较基准、独有提交与关系证据 | 独立审核的本地分支删除、squash/PR 辅助证据 |
| 恢复与历史 | 持久化操作记录；区分 Trash、保留分支、备份和不可恢复操作 | 已验证 bundle、项目归档、受限的一键恢复 |
| 集成 | 本机 Git；Mole 存在性与能力验证、用户主动启用；精确执行取决于适配器验证 | Worktrunk、gfold、托管平台只读信息 |
| 保护 | 手动 Protect/Pin、未知状态阻断、计划失效重算 | 文档化活动 lease、更多工具状态来源 |

MVP 不以“支持清理目录数量”作为完成标准。先把少量高频场景做可靠，再增加目录和适配器。

### 暂不纳入首版

全盘/整个 Home 自动清扫、系统优化、内存清理、完整卸载器、远程分支删除、自动 stash/commit、强制删除、自动结束进程、自动安装工具、自动执行项目脚本、后台定时删除、AI 会话内容扫描，以及内置终端或 agent 编排。

完整仓库/主 checkout 的删除与项目休眠也不走普通 worktree 移除流程，留给单独的归档设计。

## 实施阶段与验收

| 阶段 | 交付目标 | 进入下一阶段的条件 |
| --- | --- | --- |
| 0 文档与技术验证 | 明确对象模型、界面原型、权限/Process 试验、MoePeek 约定映射、Mole 能力矩阵 | 关键假设有记录；不把未验证能力写成已支持 |
| 1 只读原型 | 选定目录发现、跨仓库 worktree 列表、证据检查器、保护与大小估算 | 不改用户状态；扫描不完整和未知状态准确；界面与资源消耗可测 |
| 2 精确产物清理 | 有限规则、明确选择、审核计划、恢复语义、执行后核验 | 一次性 fixtures 验证范围、取消与失败；适配器无法限域时不开放执行 |
| 3 受限退役 MVP | clean linked worktree 移除并保留分支、临近复查、持久日志与结果核验 | 忽略/独有/复杂状态得到保护；部分失败与重启可解释 |
| 4 历史管理 | 独立本地分支删除、仓库级 prune 审核、受限 bundle 与重建 checkout | 批量 ref 关系和恢复前置条件经过测试 |
| 5 扩展能力 | Worktrunk/gfold、PR 只读证据、更多开发产物与共享缓存、项目休眠 | 每个集成独立通过范围、版本、权限和恢复评审 |

安装、构建与验证状态以当前 [README](../README.md) 和逐版本记录为准；规划中的范围、性能目标与阶段名称不构成已交付声明。

### 必须覆盖的测试

- 路径：空格、换行、Unicode、控制字符、大小写敏感卷、符号链接替换、已移动 Git 目录
- Git：普通/linked/bare/独立同 remote clone、detached HEAD、独有提交、squash/rebase、合并中的仓库
- 本地数据：ignored `.env`、数据库、tracked 文件混入产物、子模块、嵌套仓库、巨大依赖目录
- 特殊状态：浅克隆、partial clone、稀疏 checkout、assume-unchanged/skip-worktree、缺失对象
- 运行环境：外接盘离线、权限不足、锁、恶意 hooks/filters、工具版本变化、输出格式漂移
- 并发与失败：审核后文件/ref 改变、多个待删 ref 互相引用、备份失败、超时、取消、崩溃、部分成功与日志恢复
- 恢复：材料缺失、checksum 不符、目标路径被占用、分支被改写、可用空间不足

所有危险测试先在可丢弃 fixtures 执行。验收看的是范围是否准确、未知是否被阻断、失败是否可解释，以及恢复能力是否只承诺实际验证过的部分。

### 性能目标需要测量

目标是空闲时不周期性全盘扫描，列表渐进显示，昂贵目录大小按需计算，后台并发有上限。同仓库修改始终串行。记录冷启动、缓存呈现、扫描耗时、文件 IO、主进程与子进程峰值内存、空闲 CPU 和能耗，再决定具体预算。

“SwiftUI 原生”“体积小”不能代替性能数据。当前不宣称任何已达到的 RAM、CPU、速度或节省空间指标。

## 原规划的下一步（历史）

先验证最关键的假设：用户能否在一张原生列表里识别项目与遗留 worktree、理解清理建议，以及明确区分“清产物”“移除 checkout”和“删分支”。同时验证本机 Git/Mole 的具体接口和权限限制，再按验收门槛逐步开放修改能力。

## 完整愿景的后续边界

可选应用管理可在核心工作区流程稳定后另行评估：先考虑库存、空间归属与用户主动打开系统入口；完整卸载和残留识别需要专门范围、权限与恢复设计，不计入 MVP。项目休眠、共享缓存、归档恢复与托管平台只读证据同样逐项验收，不扩展成全面系统优化或后台自动清扫。
