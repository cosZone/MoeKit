# 产品定位与对象模型

状态：planned。本文是产品与实施蓝图，尚无可运行应用或已验证的执行能力。

## 为什么做这个项目

开发者的空间问题往往和工作区生命周期连在一起：同一个仓库有多个临时 checkout，构建产物和依赖分散在不同目录，已经结束的工作仍占用磁盘，而少量未提交文件、忽略文件或独有提交又让直接删除变得危险。

MoeTidy 的核心体验是：**找到工作区 → 看懂状态与空间 → 选择精确动作 → 审核影响 → 执行并核验 → 保留可用的恢复信息。**

现有产品已经提供原生界面、开发缓存清理、worktree 管理、合并判断和项目归档。我们的目标是把这些能力组织成连贯、透明、保守的工作流程，并尽量复用用户已经安装的可靠工具。是否真正更好，需要用真实任务、兼容性测试和性能测量证明。

## 三个要解决的实际问题

### 项目还在做，只想回收开发产物

从项目详情看到各个 checkout 的构建输出、依赖目录及大小估算。优先审查已验证规则识别的可重建产物，保留源码、Git 元数据和未经确认的本地数据。操作前说明重新构建、重新下载及版本不可完全复现的可能成本。

### 临时工作区已经结束，想放心收尾

跨仓库找到遗留的 worktree，分别查看工作目录改动、忽略文件、独有提交、分支关系、锁和活动迹象。默认选择“移除 checkout，保留分支”；“同时删除本地分支”是另一项需要独立证据和审核的动作。

### 过了一段时间，想知道发生过什么

从历史中确认清理了哪些路径、使用了哪个工具、哪些项目失败、保留了哪些分支或归档。只有具备对应恢复材料且通过检查的操作才提供恢复入口；普通日志和删除清单不能代替备份。

## 产品原则

- **以项目和工作区为中心。** 用户面对的是自己的工作，不需要先理解每个底层 CLI
- **本机优先。** 文件内容、仓库路径和操作记录默认留在本机；联网能力单独启用
- **有边界的发现。** 从用户选择的目录开始，显示扫描范围、遗漏与权限问题
- **证据先于建议。** 每条建议都能回答“为什么出现”“将失去什么”“会留下什么”
- **不确定就暂停。** 超时、解析失败、权限不足和不支持的 Git 布局显示为“未知”，不会变成可清理状态
- **复用能力，保留责任。** 外部工具负责它擅长的事情，应用仍负责作用域、审核、复查、结果核验和准确描述
- **原生而克制。** 主界面是一张好用的工作区列表，不堆叠健康分数、仪表盘卡片或一键系统优化

## 统一的数据与操作模型

| 对象 | 表达的内容 | 计划允许的动作 |
| --- | --- | --- |
| 项目 Project | 用户认知中的一个项目，可关联一个或多个独立仓库 | 添加、分组、保护、查看空间 |
| 仓库 Repository | 一个真实 Git common directory 对应的历史和引用集合 | 检查、设置比较基准、查看分支与 worktree |
| 工作区 Workspace | 主 checkout 或 linked worktree；可显示非 Git 项目目录 | 打开、保护、检查产物；符合条件时退役 linked worktree |
| 产物 Artifact | 工作区内被规则或适配器识别的明确文件/目录 | 查看依据、加入审核、按已验证方式清理 |
| 分支 Branch | 本地 ref、tip 与比较关系，独立于 checkout 的存在 | 查看；后续独立审核删除本地分支 |
| 操作计划 Plan | 固定范围、证据快照、恢复选择与执行顺序 | 审核、失效重算、逐项执行、核验 |
| 操作记录 Operation | 实际结果、失败原因与恢复材料的索引 | 查询；满足条件时重新创建或恢复 |

两个指向相同 remote URL 的独立 clone 仍是两个仓库。linked worktree 按 common directory 的真实身份归组，不能按仓库名合并。共享 Git 对象库不重复计入每个 checkout 的空间。

同一路径也不能既作为“清理产物”又作为“退役工作区”重复结算。计划器需要消除父子路径重叠，并展示最终实际影响集合。
